    <h1>Day 8 — Database Scaling & Replication</h1>


    <div class="subtitle">

        AI Engineer System Design — Beginner → Advanced

    </div>


    <h2>1. Why Databases Become a Bottleneck</h2>


    <p>

        In a scalable AI application, the application layer can often be

        horizontally scaled by adding more FastAPI instances.

    </p>


    <p>

        However, the database can eventually become the bottleneck.

    </p>


    <div class="architecture">

10,000 requests/sec

        ↓

     FastAPI

        ↓

   PostgreSQL

        ↓

CPU = 95%

Connections = 4,000

Latency = 2 seconds

    </div>


    <p>

        Adding more FastAPI servers will not solve this problem if PostgreSQL

        is the actual bottleneck.

    </p>


    <div class="important">

        <strong>Key principle:</strong>

        Scale the bottleneck, not the component that is easiest to scale.

    </div>



    <h2>2. Read-Heavy vs Write-Heavy Workloads</h2>


    <p>

        One of the first things to identify in a system design interview is

        whether the workload is read-heavy, write-heavy, or balanced.

    </p>


    <div class="concept">

        <strong>Read-heavy example:</strong><br><br>

        10,000 DB operations/sec<br>

        9,000 reads<br>

        1,000 writes

    </div>


    <p>

        For a read-heavy system, read replicas are often an effective scaling

        strategy.

    </p>


    <div class="architecture">

                Primary

               /   |   \

              ↓    ↓    ↓

             R1   R2    R3


Primary → Writes

R1/R2/R3 → Reads

    </div>



    <h2>3. Database Replication</h2>


    <p>

        Replication means maintaining copies of database data on other

        database servers.

    </p>


    <div class="architecture">

                 PostgreSQL

                   Primary

                  /   |   \

                 ↓    ↓    ↓

                R1   R2    R3

    </div>


    <p>

        The primary database generally handles writes while replicas can

        handle read traffic.

    </p>


    <p>

        This allows read traffic to be distributed across multiple machines.

    </p>



    <h2>4. Asynchronous vs Synchronous Replication</h2>


    <h3>Asynchronous Replication</h3>


    <p>

        With asynchronous replication, the primary can return a response

        without waiting for every replica to acknowledge the write.

    </p>


    <div class="architecture">

Application

    ↓

Primary

    ↓

Response returned

    ↓

Replicas catch up

    </div>


    <p><strong>Advantages:</strong></p>


    <ul>

        <li>Lower write latency</li>

        <li>Higher throughput</li>

        <li>Better scalability</li>

    </ul>


    <p><strong>Disadvantage:</strong></p>


    <p>

        Replicas can temporarily contain stale data.

    </p>



    <h3>Synchronous Replication</h3>


    <p>

        With synchronous replication, the primary waits for the required

        replica acknowledgement before completing the operation.

    </p>


    <div class="architecture">

Application

      ↓

   Primary

      ↓

   Replica

      ↓

Acknowledgement

      ↓

 Response

    </div>


    <p><strong>Advantages:</strong></p>


    <ul>

        <li>Stronger consistency</li>

        <li>Lower chance of losing acknowledged data depending on configuration</li>

    </ul>


    <p><strong>Disadvantages:</strong></p>


    <ul>

        <li>Higher latency</li>

        <li>More coordination</li>

        <li>Potential availability impact if required replicas are unavailable</li>

    </ul>



    <h2>5. Replication Lag</h2>


    <p>

        Replication lag occurs when a replica has not yet caught up with the

        primary.

    </p>


    <div class="architecture">

Primary:


Message 1

Message 2

Message 3

Message 4



Replica:


Message 1

Message 2

Message 3

    </div>


    <p>

        The replica is missing Message 4.

    </p>


    <p>

        The difference between the primary and replica state is replication

        lag.

    </p>


    <h3>Why is this important for AI systems?</h3>


    <p>

        Consider an AI chat application.

    </p>


    <div class="architecture">

User:

"Remember that my preferred language is Python."


        ↓


Write → Primary


        ↓


Immediately:


User:

"What programming language do I prefer?"


        ↓


Read → Replica

    </div>


    <p>

        If the replica has not caught up, the AI system could retrieve stale

        conversation information and generate an incorrect response.

    </p>



    <h2>6. Read-After-Write Consistency</h2>


    <p>

        Read-after-write consistency means that after a user successfully

        performs a write, their subsequent read should reflect that write.

    </p>


    <div class="important">

        <strong>Example:</strong><br><br>

        User writes X → User immediately reads X<br><br>

        The user expects the read to contain the latest value of X.

    </div>


    <p>

        With asynchronous replicas, this guarantee is not automatically

        provided.

    </p>



    <h2>7. How Can We Solve Read-After-Write Problems?</h2>


    <h3>Option 1 — Read From Primary</h3>


    <div class="architecture">

Write → Primary


Critical Read → Primary

    </div>


    <p>

        This provides strong consistency but increases the load on the

        primary.

    </p>



    <h3>Option 2 — Session Stickiness</h3>


    <p>

        After a user writes, subsequent reads can temporarily be routed to

        the primary.

    </p>


    <div class="architecture">

User

 ↓

Primary


Write

 ↓

Primary


Subsequent reads

 ↓

Primary

    </div>



    <h3>Option 3 — Lag-Aware Routing</h3>


    <p>

        Monitor the replication lag of every replica.

    </p>


    <div class="architecture">

Replica 1 → 5 seconds behind   → ❌ Don't use


Replica 2 → 100 ms behind      → ✅ Use


Replica 3 → 50 ms behind       → ✅ Use

    </div>


    <p>

        If the system requires data to be no more than one second stale,

        Replica 1 should not receive that read.

    </p>



    <h3>Option 4 — Wait for Replication</h3>


    <p>

        The system can wait until the replica catches up before serving the

        read.

    </p>


    <p>

        This improves consistency but increases latency.

    </p>



    <h2>8. Connection Pooling</h2>


    <p>

        Creating a new database connection for every request is expensive.

    </p>


    <div class="architecture">

Request

   ↓

Create connection

   ↓

Query

   ↓

Close connection

    </div>


    <p>

        Instead, we can maintain a pool of reusable connections.

    </p>


    <div class="architecture">

FastAPI

   ↓

Connection Pool

   ↓

┌────┬────┬────┬────┐

 C1   C2   C3   C4

    </div>


    <p>

        Connections can be reused across requests.

    </p>


    <div class="important">

        <strong>Important:</strong>

        Increasing the connection pool size does not automatically increase

        database capacity.

    </div>


    <p>

        If PostgreSQL is already CPU-bound, increasing connections can create

        more contention and potentially make performance worse.

    </p>



    <h2>9. Database Partitioning</h2>


    <p>

        Suppose an AI chat application has billions of messages.

        Managing the entire dataset as one huge table can become difficult.

    </p>


    <p>

        Partitioning divides a large logical table into smaller physical

        pieces.

    </p>


    <div class="architecture">

messages

   ├── messages_2025

   ├── messages_2026

   └── messages_2027

    </div>


    <p>

        Partitioning can also be based on other logical criteria depending

        on the access pattern.

    </p>



    <h2>10. Partitioning vs Sharding</h2>


    <h3>Partitioning</h3>


    <p>

        Partitioning generally divides data within the database system.

    </p>


    <div class="architecture">

One PostgreSQL system


        messages

       /   |   \

      P1   P2   P3

    </div>



    <h3>Sharding</h3>


    <p>

        Sharding distributes data across multiple database systems.

    </p>


    <div class="architecture">

                Application

                    ↓

                Shard Router

              /      |      \

             ↓       ↓       ↓

          DB-1     DB-2     DB-3

    </div>



    <h2>11. Choosing a Shard Key</h2>


    <p>

        Suppose we are building a large AI chat system.

    </p>


    <p>

        One possible shard key is:

    </p>


    <div class="concept">

        <strong>user_id</strong>

    </div>


    <p>

        This can work well when most queries are scoped to a particular user.

    </p>


    <div class="architecture">

User 101 → DB1

User 102 → DB2

User 103 → DB3

    </div>


    <p>

        However, we need to be careful about users with extremely high

        traffic.

    </p>


    <div class="architecture">

User A → 10 million requests


Other users → 100 requests each

    </div>


    <p>

        This can create a hot shard.

    </p>



    <h2>12. Characteristics of a Good Shard Key</h2>


    <h3>High Cardinality</h3>


    <p>

        A good shard key should have many possible values.

    </p>


    <p>

        user_id is generally more suitable than country because a small

        number of countries could contain a very large percentage of users.

    </p>


    <h3>Even Distribution</h3>


    <p>

        Ideally traffic should be distributed relatively evenly.

    </p>


    <div class="architecture">

Shard 1 → ~33%

Shard 2 → ~33%

Shard 3 → ~33%

    </div>


    <p>

        Avoid situations such as:

    </p>


    <div class="architecture">

Shard 1 → 80%

Shard 2 → 10%

Shard 3 → 10%

    </div>


    <h3>Query Locality</h3>


    <p>

        Queries should ideally be able to find the required data without

        contacting every shard.

    </p>



    <h2>13. Why Don't We Immediately Shard Everything?</h2>


    <p>

        Sharding provides scalability but introduces significant complexity.

    </p>


    <ul>

        <li>Cross-shard queries</li>

        <li>Distributed transactions</li>

        <li>Rebalancing</li>

        <li>Hot shards</li>

        <li>More complicated backups</li>

        <li>More complicated monitoring</li>

        <li>More complicated debugging</li>

        <li>Data migration</li>

    </ul>


    <div class="important">

        <strong>Principle:</strong>

        Don't introduce sharding until simpler scaling techniques are

        insufficient.

    </div>



    <h2>14. Database Scaling Progression</h2>


    <div class="architecture">

Slow Query

    ↓

Optimize Query

    ↓

Indexes

    ↓

Connection Pooling

    ↓

Redis Cache

    ↓

Read Replicas

    ↓

Partitioning

    ↓

Sharding

    </div>


    <p>

        Not every system needs to reach sharding.

    </p>



    <h2>15. Database Scaling in an AI System</h2>


    <p>

        Consider an AI chat application:

    </p>


    <div class="architecture">

User

 ↓

API Gateway

 ↓

Load Balancer

 ↓

FastAPI

 ↓

Redis

 ↓

PostgreSQL

 ↓

Qdrant

 ↓

LLM

    </div>


    <p>

        Database scaling might look like:

    </p>


    <div class="architecture">

                    FastAPI

                       |

             ┌─────────┴─────────┐

             ↓                   ↓

          Writes               Reads

             ↓                   ↓

          Primary       ┌────────┼────────┐

                        ↓        ↓        ↓

                       R1       R2       R3

    </div>


    <p>

        The AI system can then use PostgreSQL for conversation and relational

        data, while Qdrant handles vector retrieval.

    </p>


    <div class="architecture">

User Query

    ↓

    ↓

    ↓

    ↓

    ↓

    </div>



    <h2>16. How to Approach Database Questions in an Interview</h2>


    <p>

        When an interviewer says:

    </p>


    <div class="concept">

        "Your database is becoming a bottleneck. What would you do?"

    </div>


    <p>

        Do not immediately say "I'll add replicas."

    </p>


    <h3>Step 1 — Identify the Workload</h3>


    <ul>

        <li>Read-heavy?</li>

        <li>Write-heavy?</li>

        <li>Mixed?</li>

    </ul>


    <h3>Step 2 — Identify the Bottleneck</h3>


    <ul>

        <li>CPU?</li>

        <li>Memory?</li>

        <li>Disk I/O?</li>

        <li>Connections?</li>

        <li>Slow queries?</li>

        <li>Lock contention?</li>

    </ul>


    <h3>Step 3 — Optimize First</h3>


    <ul>

        <li>Query optimization</li>

        <li>Indexes</li>

        <li>Connection pooling</li>

        <li>Caching</li>

    </ul>


    <h3>Step 4 — Scale</h3>


    <ul>

        <li>Read replicas</li>

        <li>Partitioning</li>

        <li>Sharding</li>

    </ul>


    <h3>Step 5 — Consider Consistency</h3>


    <p>

        Ask:

    </p>


    <div class="important">

        Can the system tolerate stale reads?

    </div>


    <p>

        If yes, replicas may be appropriate.

    </p>


    <p>

        If no, primary reads or consistency-aware routing may be necessary.

    </p>


    <h3>Step 6 — Consider AI-Specific Requirements</h3>


    <ul>

        <li>Does conversation history need strong consistency?</li>

        <li>Can RAG metadata be eventually consistent?</li>

        <li>How fresh does the knowledge base need to be?</li>

        <li>Can LLM responses be cached?</li>

        <li>Can requests be processed asynchronously?</li>

    </ul>



    <h2>17. Day 8 Key Concepts</h2>


    <div class="summary">


        <h3>Database Scaling</h3>


        <p>

            Optimize → Index → Pool → Cache → Replicate → Partition → Shard

        </p>


        <h3>Replication</h3>


        <p>

            Primary → Writes<br>

            Replicas → Reads

        </p>


        <h3>Important Problems</h3>


        <ul>

            <li>Replication lag</li>

            <li>Read-after-write consistency</li>

            <li>Hot shards</li>

            <li>Connection exhaustion</li>

            <li>Lock contention</li>

        </ul>


        <h3>Most Important Principle</h3>


        <p>

            <strong>

                First identify the workload and bottleneck.

                Then choose the simplest architecture that solves the problem.

            </strong>

        </p>


    </div>
